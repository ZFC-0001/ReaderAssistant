# 架构与联调

## 目录与依赖

```text
contract/                 三人共享，B维护
capture/ + inference/     A：采集、OCR、小模型、时间和关联建议
business/                 B：协调、策略、用例与提交门禁
data/ + data/local/       B：设置、Room、持久上下文
reminder/                 B：平台提醒、outbox和广播
presentation/             C：界面、ViewModel和操作转发
bootstrap/                B：应用级装配
```

C 仅依赖 contract/ 与装配入口；A 的模型/采集不直接访问 Room；B 是唯一业务写库入口。bootstrap 把接口与实现组装为应用级对象。

先保留一个 app Gradle 模块，按包明确职责。没有要求三人各做一个独立 App，也不立即拆大量模块。可通过 scripts/check-boundaries.py 检查主要导入边界。

## 已借鉴 ReaderTest 的经验

- QQ 已测可读，微信聊天已测无障碍失败：当前只读取 QQ，微信 OCR 单独实现和验证。
- 延迟600ms、事件节流1秒、轮询2.5秒作为起始参数；不是所有设备的最佳参数。
- 活动包名必须和目标一致；新配置显式加入交互窗口检索标志，但不把它当作微信可读证明。
- 不再用全局可变 CaptureBuffer 做业务状态源，不依赖 Activity 每2秒全量提取。
- 保留文本块和截断标记；原型的1000字全屏拼接、前30字内存去重不作为正式机制。
- 取消/延期不能被词表直接过滤；只有日期不能补成23:59。
- 异步广播 goAsync/finish；闹钟登记、广播到达与可见通知分开验收。
- 原 ReminderScheduler 的 schedule/cancel Intent 身份不一致，后续实现须统一。
- 原 ReminderReceiver 提前标记已触发并吞通知异常的做法不沿用。

`reference/ReaderTest/` 是本次源文件快照，仅供参考，不编译、不当作通过审查的成品代码。

## 最短联调路径

1. 启动 app → 首页载入明确标注的样例 → 待确认出现一项。
2. 进入详情记录任务 ID → 确认 → 正式待办查看相同 ID、递增版本。
3. 再次点载入样例，不新增记录；重启后重复载入也不新增。
4. 完成任务，状态变为已完成；相关详细来源清理，摘要/去重标记保留。
5. 在设置选择 QQ 并开启，系统手动启用无障碍。读到内容时模型状态仍为未接入，不生成伪 AI 任务。

这条路径用于验证骨架接线，不代表微信、模型、正式变更、提醒已经完成。自动超时和跨应用卡片待对应 TODO 实现。

## 并发和隐私边界

- 模型调用在业务锁外；提交与设置变更在同一业务锁内，提交前复核 session/应用/来源时效。
- 采集默认关闭；用户必须同时选择应用并完成系统授权。检测桌面只用必要窗口元数据。
- 主线程不跑模型/数据库；队列有界，满时计数并提示。更完善的补采由 A-05 实现。
- 不声明 INTERNET，关闭备份，不记录原文日志；第三方依赖、内存图片和缓存仍须隐私验收。
- 应用 scope 在进程活着时独立于 Activity；它本身不是进程保活或强停后恢复保证。
- 任务清理后仍保留必要摘要与去重。共享来源不能从已结束任务详情泄露；完整访问门禁/恢复清理竞争由 B-08 完成。

UI 使用 Views 联调占位；Compose、Hilt、DataStore 是后续可替换实现点，不冒充已接入。模型/OCR依赖尚未选定，必须先测首次离线、资源成本及目标场景可读性。变更/恢复、提示投递、提醒与清理的表和接口已留出，但完整事务还没实现。
